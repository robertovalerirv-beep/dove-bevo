# App-only low-zoom priced markers: design hold

**Status: HOLD.** This document is a draft implementation contract, not a deployed API or a claim that the low-zoom map is covered. Do not register `/api/mobile/v2/markers`, apply a migration, or make the native client call it until the seed, freshness and source-coverage tests below pass on the same commit. The existing website interface and legacy EUR price contract remain unchanged.

## Why this needs a separate index

The map currently stops loading static cells below zoom 13 (`src/app/app.tsx`), so an app overlay drawn only from loaded cells cannot tell a customer which venues have prices across a city. The existing menu and mobile price APIs page inside **one geohash-5 cell**. They cannot answer a bounded city viewport without requesting many cells or claiming that an incomplete page is complete.

Coordinates and current price evidence live in different places:

| Venue / price source | Canonical position | Public price condition |
| --- | --- | --- |
| Italian OSM venue with a website customer price | `data/<DATA_VERSION>/v/<cell>.json`, generated at deploy | `prices_current.status='active'`, approved user or current static identity, not hidden |
| Approved user venue with a website customer price | `venues_user` | `venues_user.status='approved'`; `prices_current.status='active'` |
| European catalogue venue with an app customer or approved menu price | deployed `mobile-data/catalog.json` | `mobile_prices_current.status='active'` and exact catalogue currency; exclude Italian keys that also exist in the current static cell |
| Italian owner venue or vetted foreign OSM venue | `mobile_menu_v2_venues` | active `mobile_menu_v2_offers` joined to an approved source, or a current active v2 customer entry |
| Italian static OSM venue with a named owner menu or v2 customer price | current static cell, not the v2 registry | active approved v2 menu offer, or latest active v2 customer entry; the key must still exist in the current static cell |

The Italian OSM cells are **not committed in Git**. `deploy-staging.yml` downloads Geofabrik data and builds `public/data/<DATA_VERSION>` anew before each deploy. A one-time SQL migration cannot know those coordinates or tell whether a previously priced OSM venue was removed in the next extract. Reading old coordinates from a prior index would be false. The catalogue is another independently versioned asset. `venues_hidden`, `mobile_venues_moderation`, offer statuses, source review statuses, customer-entry revisions and current prices can change after a seed.

## Proposed implementation

1. Add a private app-only `mobile_marker_positions` table for static Italian OSM and catalogue venue positions, keyed by immutable `snapshot_id, venue_key`. Store `cell, lat, lon, position_source` and add both `(snapshot_id, lat, lon, venue_key)` and `(snapshot_id, lon, lat, venue_key)` indexes. A separate `mobile_marker_snapshots` row records the exact `DATA_VERSION`, catalogue version and catalogue SHA-256, static cell manifest hash, expected row count, actual row count and `ready_at`. `ready_at` is set **only after** all rows and hashes have been checked. Keep the previous snapshot through deployment so old Workers continue to work during rollout. Do not use an index containing only venues priced at seed time: a customer can add the first price later.
2. In the existing deploy pipeline, after the OSM import and before deploying the new Worker, generate a deterministic, bounded SQL/NDJSON seed from every versioned cell and the validated catalogue. Validate geohash-to-cell, unique key, coordinate range and generated version. Apply to the existing D1 in batches with retryable idempotency and exact counts. A failed or partial seed fails the deploy; never mark it ready. Keep the seed as an ephemeral build artifact in the selected project workspace for local work and in the CI runner's existing temporary directory for hosted deployment. Do not create another Cloudflare resource or store secrets in the seed.
3. For dynamic `venues_user` and `mobile_menu_v2_venues`, add bounded coordinate indexes and read their positions directly, or maintain them with additive D1 triggers; decide from `EXPLAIN QUERY PLAN` and a representative dense-city test. Existing indexes cover cell, not latitude/longitude. Do not copy a user venue as public until its status is approved. Owner-verified venues must retain the existing near-duplicate exclusion. When an owner venue duplicates a current static or user venue, suppress the owner marker rather than show both.
4. At request time, load the deployed `DATA_VERSION` and catalogue version, require an exact ready snapshot, and query candidate positions inside a validated bbox. Join/`EXISTS` against the **current** price and moderation tables, rather than materializing mutable price flags. Filter active website prices, active catalogue app prices, active approved named-menu offers, and **only the latest public v2 customer revision per item**; the linked offer must still be active and approved. Exclude hidden/moderated/removed venues and a static key absent from the current snapshot. Return 503 with `Cache-Control: no-store` when snapshot readiness or asset version does not match. A stale index must never be silently served.
5. Add `GET /api/mobile/v2/markers?bbox=s,w,n,e&category=<catalog-code>&after=<opaque>&limit=<1..100>` behind the existing origin and read-rate guards. Require one finite, ordinary non-crossing bbox with `-90<=s<n<=90`, `-180<=w<e<=180` and a documented maximum span/area. Use a stable keyset sorted by `venue_key` or `(cell, venue_key)` across all source branches; the cursor binds bbox, category and snapshot identity. Fetch `limit+1` **public** rows to calculate `has_more`, so a page with filtered or hidden candidates does not falsely terminate. Reject malformed/duplicate query parameters and mismatched cursors. For each result return key, cell, coordinates, original currency or a list of currencies, and source/provenance flags; do not return a single numeric price where servings, happy-hour conditions, fees or GBP/EUR are incomparable. Return `coverage: {partial: true, reason: 'priced_venues_only'}` and `next_after`; do not assert city totals or comprehensive menu coverage.
6. Only after the API is seeded, deployed and read back on a real dense city should the native low-zoom overlay be switched on. The client should debounce viewport changes, cancel obsolete requests, paginate or display an honest “more priced places in this area” state, and retain existing high-zoom cell behavior. Never interpret page count as the total number of venues.

## Release tests and required evidence

- Fixture with all five source classes above, EUR and GBP, no fabricated price: each active source appears once in an encompassing viewport and under its category; absent category remains absent. A venue with two sources remains one marker with both provenance flags.
- Latest v2 customer revision wins: `active -> review`, `active -> removed`, and a superseding active amount do not leak an older amount. An unapproved or removed linked offer is hidden. A held source is never included.
- Hidden and moderated venues, pending/removed user venues, and a static OSM key deleted from the next version's cell are absent. Owner near-duplicates follow the existing v2 venue resolver's rule.
- Exact bbox boundaries, narrow city boxes, duplicate parameters, bad numeric values, oversized boxes, cursor/filter/version mismatch, empty page, 100/101-row boundary and no duplicate/skip across pages. The query must be bounded by the coordinate index before price joins; record `EXPLAIN QUERY PLAN` and D1 read/CPU measurements on Rome, Milan, Naples and Turin fixture shapes.
- Seed count and SHA-256 checks fail closed on a missing cell, malformed row, duplicate key, interrupted D1 batch, catalogue mismatch and pending deployment. A new static version has no ready snapshot until its seed is complete; the old version stays readable until the new Worker is healthy.
- Verify no website route, website UI, legacy EUR table, existing price response or old cell endpoint changes. Run the worker test project, typecheck, exact-head CI and an authenticated staging read-back before native beta distribution.

## Current hold and next owner

This branch establishes the source-of-truth and release contract only. The missing generated static assets, seed-to-deploy ordering and all-source public-price predicate have not yet been verified together. **Do not merge as an implementation or claim low-zoom coverage.** Next implementation owner should build the deterministic seed and in-memory/local-D1 fixtures first, then the additive migration and route, run the tests above, have an independent reviewer inspect the exclusion rules and only then integrate the app overlay. The project repository remains canonical; this draft stays on a separate selected-OneDrive worktree and GitHub draft PR.
