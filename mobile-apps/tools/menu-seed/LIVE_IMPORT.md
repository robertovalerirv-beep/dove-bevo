# Guarded one-off online-menu import

This is a separate, operator-controlled tool for an explicitly authorized batch. It does not modify the website, routes, schema or resources. Dry run is the default and performs public GETs and read-only, cohort-key D1 SELECTs. `--apply` requires the exact SHA-256 of the manifest bytes. This hash binds reviewed bytes; it is not independent evidence of authorization or source truth. The operator must curate and approve each menu price, primary Google count and venue identity before applying. Neither Google assertions nor `identity_note` are independently verified by this program. Do not run against fabricated venues or prices.

The fixed target is staging's existing D1 database `d2d4f6d4-b2fb-435b-9f9e-a2961d9c9839`, serving `https://www.dovebevo.com`. The tool checks its public health data version, downloads the matching static cell JSON and compares the existing OSM key, name, coordinates, city and numeric kind. It downloads each HTTPS menu source and verifies the explicitly selected SHA-256 pin described below. Redirects are rejected; source URLs may have no credentials, query or fragment. A source hash proves equality under the selected representation only, not a venue, price, copyright permission or origin of data. Before any provider attestation or D1 query, all source pins must match. Authenticated read-only Cloudflare checks must then verify the Worker DB binding, the exact custom domain, service and `production` environment, and database UUID and name. Only a small verified summary is retained in the receipt; full Worker settings are never recorded. Denied reads or a legacy route lacking the custom-domain record fail closed. These checks require suitable provider read permissions and do not create or modify provider configuration.

Manifest UTF-8 JSON has exactly `schema_version`, `batch_id`, `checked_on`, `data_version`, and `records`. The version is integer 1 or 2, date is actual review date (not in the future), data version is eight digits, and 1–200 records are supported. Each version 1 record has exactly:

```
venue_key name cell city lat lon drink hh cents source_url source_sha256
 google_reviews google_url identity_note
```

Each version 2 record requires those same fields plus `source_format`, which is exactly `raw` or `html_text_v1`. Version1 always uses raw bytes and rejects the extra field. Version2 never selects a format automatically or falls back after a mismatch. `source_sha256` is lowercase hex of the representation selected for that record:

- `raw`: SHA-256 of the complete downloaded response bytes, unchanged from version 1. Keep JavaScript, PDFs and other binary assets in this format.
- `html_text_v1`: strictly decode the complete response as UTF-8; pass it through Python's standard `HTMLParser(convert_charrefs=True)`; retain text data except within `script` and `style`; join retained chunks with one ASCII space; replace each run matching Python `\s+` with one ASCII space and trim; encode as UTF-8 and hash. Comments, tag attributes and script/style content do not participate. This accommodates per-request HTML wrapper identifiers while a changed menu amount still changes the pin. Sources are limited to 8 MiB. Extracted text is bounded to 1 MiB of intermediate characters and 1 MiB of canonical UTF-8; empty text or invalid UTF-8 is rejected. No content is truncated to make a pin match.

Extracted HTML text may include hidden markup or omit JavaScript-rendered content. It is **not** a browser-visible text assertion, a price extractor or proof of price meaning. The curator must inspect the actual menu and independently approve its facts, and must retain the source response's raw hash separately when using a text pin. The manifest pin binds the chosen representation, while the apply approval still binds every exact manifest byte. The in-run digest cache is keyed by both source URL and format, so two formats cannot reuse each other's digest. Use `source_digest(source_bytes, "html_text_v1")` from `live_import.py` to reproduce the exact text-pin algorithm for a reviewed local response.

`venue_key` is a canonical positive OSM node, way or relation ID; `cell` is the matching geohash5; `city` is the published city ID or null for no city. `hh` is 0 or 1, `cents` an integer in the existing category's inclusive EUR bounds, and `google_reviews` an integer above 100. `identity_note` records manual evidence connecting the official venue and primary Google location. The `google_url` must be a direct supported Google host. The operator is responsible for verifying price meaning, exact drink/serving, happy-hour conditions, currency and capture recency. Blank public catalogue addresses do not automatically reject a venue; a real identity review is essential. Never include credentials, private data or auth-bearing URLs.

With existing authorized Cloudflare credentials exposed only as `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN` environment variables, run from the repository root. The tool never prints values or raw HTTP errors. Receipt path must be new; reserve it in a protected working location under the selected project folder.

```powershell
python -B mobile-apps/tools/menu-seed/live_import.py --manifest <manifest.json> --receipt <new-dry-receipt.json>
python -B mobile-apps/tools/menu-seed/live_import.py --manifest <manifest.json> --receipt <new-apply-receipt.json> --apply --approved-sha256 <reviewed-manifest-byte-sha256>
python -B -m unittest discover -s mobile-apps/tools/menu-seed -p test_live_import.py -v
```

Apply performs a parameterized `INSERT ... SELECT ... WHERE NOT EXISTS ... RETURNING` per item. In the same statement it blocks any existing price in any status for that key/drink/band, any matching history, any venue report and any hidden venue. It never updates customer prices or confirmations and does not insert fabricated observations. The existing schema requires `source='manual'`: here that means a curated manual transcription of an online menu, **not** a verified visit or photograph. The manifest and receipt together retain `online_menu` provenance; the database alone does not. The receipt reports before/after scoped state and actual returned inserts; concurrent user writes can occur and these observations are not a proof that no unrelated mutation occurred.

Each affected cell's existing snapshot is invalidated using the application's version bump. Cache failure makes the receipt incomplete. A rerun with the same manifest and approval skips existing rows and retries invalidation for matching manual/date/price rows, without claiming those rows were inserted in this run. Matching rows alone cannot prove they originated in the earlier run. An insert whose response is lost is recorded as `indeterminate` and its cell invalidation is attempted. Network interruption, process termination, or receipt write failure can leave partial inserts or an empty receipt; stop, preserve evidence and use a fresh receipt for a reviewed rerun. Edge caching can continue to show old data temporarily; independently read the public site after the cache TTL before claiming visible completion. No public write was performed by the tests, which use an injected in-memory transport and SQLite.
