# Mobile menu v2 guarded one-off import

This package imports factual named drink-menu offers for the **phone apps only**. It does not write Roberto's website tables, public legacy EUR prices, customer submissions, or review counts. A checked source is not a customer observation. It has no fabricated visit date, confirmation or Google review count.

## Direct JPEG owner menus

`jpeg_image_v1` supports a venue-linked menu that exists only as JPEG images. Record the current venue-site → QR/menu page → final image link chain in the source review. The manifest must use each direct HTTPS `.jpg` or `.jpeg` asset without a query. The protected importer does not follow redirects. It checks public DNS, the 8 MiB size limit, `image/jpeg` MIME, JPEG marker/frame/scan structure and the exact raw SHA-256; it never runs page JavaScript, OCR or image decoding.

Each JPEG source has `image_evidence`, one `{ "offer_id": "offer-id", "line": "Beer name | 25 cl | EUR 3.50" }` per offer. Each line is a concise human transcription of the printed name, serving if claimed, and original currency/price. Its offer uses exactly `JPEG image: ` plus that line as `evidence_ref`. The source's `source_text_sha256` is the SHA-256 of canonical UTF-8 JSON `{ "jpeg_sha256": "<source_sha256>", "evidence": <image_evidence sorted by offer_id> }` with sorted keys, no insignificant whitespace and unescaped Unicode; `jpeg_review_digest` computes it. This existing D1 column holds a digest of raw bytes and reviewed evidence, not OCR text. JPEG sources admit regular offers only; fees, fee coverage and conditional prices need another reviewed format. Changed image bytes, incomplete evidence and source-ID reuse with different evidence fail. A machine check cannot verify a transcription against pixels, so an independent reviewer must compare every row with the exact pinned image before merge or seed. Keep source images and OCR output out of the repository.

## Manifest

Store a UTF-8 JSON manifest at `mobile-apps/data/mobile-menu-v2-seeds/<SHA-256-of-exact-file>.json`. Version 1 has `batch_id`, `checked_on`, `data_version`, and arrays `venues`, `sources`, `offers`, `fees`, `fee_coverage`. It may also have a `minimum_spends` array; older exact manifests remain valid without that field. The importer validates exact object fields and rejects duplicate JSON keys. Use one immutable source row per venue/source-text snapshot. A later changed menu or held-to-approved use decision needs a new source ID and new manifest; D1 rejects UPDATE/DELETE of source snapshots.

A venue uses either:

- `osm_static`: an existing Italian OSM n/w/r key whose exact name, coordinates, kind, address and city match Roberto's currently published static cell. It creates no v2 registry row.
- `owner_verified`: a new Italian branch absent from static data, with a venue-owned HTTPS location page, exact visible name and address, OSM address-node coordinates, pinned owner-page visible-text hash and pinned `osm_node_v1` semantic SHA-256 of OSM node ID, version, coordinates and sorted tags (ignoring XML generator, ordering and numeric trailing zeroes). Key is `m` plus the first 24 hex digits of SHA-256 of `dovebevo-v2-owner-it\n<canonical owner URL>\n<normalized address>`. It creates an app-only registry row. Any same-name venue within 50 m, any venue within 15 m, or cell-boundary ambiguity is held.
  `osm_node_v1` uses canonical UTF-8 JSON of `{id, version, lat, lon, tags}`. XML body length, DTD, multiple nodes and duplicate tags are rejected. A node edit requires a new reviewed manifest; the protected audit checks that backend D1 admits this new hash basis before any owner-verified seed.
- `osm_external`: a non-Italian OSM node with exact OSM name and coordinates; it creates an app-only registry row. No Google review count is required.

Each approved source has an HTTPS owner-linked menu URL, format `html_text_v1`, `pdf_text_v1`, `pdf_image_v1`, `jpeg_image_v1` or the narrowly scoped `json_menu_v1`, pinned raw/content SHA-256, checked date and recorded source-use basis/reference/review date. The HTML hash follows the existing v1 visible-text normalization. Text PDF hashes pin both raw bytes and whitespace-normalized `pdftotext -layout` output. For `json_menu_v1`, only Carico Milano's first-party `https://www.carico.io/api/menu` endpoint is accepted. The raw JSON SHA-256 is pinned in both source hash fields. The importer checks the exact set of visible, available, strictly numeric-priced drink items against manifest names, EUR amounts, menu categories and serving labels; food, hidden, unavailable and unpriced items are excluded. Any menu byte change, unknown category, ambiguous price or missing/extra offer stops the protected run. The venue website renderer `/js/app.js` supplies the EUR symbol, and its exact raw SHA-256 is pinned by the protected importer. This format does not copy descriptions or images. `held` is recorded as a review outcome but **cannot seed**, and an offer or fee may reference only an approved source. Restricted Leggimenu, YHOP, Metropolita, Jungle Juice and Google-source URLs are rejected. Protected runs refuse IP-literal, local and private DNS targets, unexpected HTML/PDF/XML content, oversized responses and HTTP redirects; page JavaScript is never executed.

The only Google-source exception is the exact September 2026 Yellow Bar Roma PDF linked from Yellowsquare's venue page. `import_v2.py` pins its direct document URL, venue, owner reference, raw PDF hash and extracted text hash. The document endpoint serves `application/octet-stream`; this exception also requires PDF bytes and accepts only that media type or `application/pdf`. All other Google documents and URL variants remain blocked. No PDF or OCR output is stored in the repository.

### Image-only owner PDFs (`pdf_image_v1`)

Use this format only when the owner PDF contains no extractable text. It requires an independently reviewed, visually inspected menu; OCR suggestions alone are insufficient. The manifest source has all ordinary source fields plus `page_count` (1–100) and `image_evidence`, one entry per offer: `{"offer_id":"offer-id","page":1,"line":"Classic Spritz | EUR 7.50"}`. The `line` is the reviewer's concise, manually checked transcription of the item and its price on that page, with the original currency written as its ISO code and a dot decimal. If a serving label is claimed, include it verbatim; if millilitres are claimed, include the explicit amount in `ml`. The corresponding offer's `evidence_ref` must be exactly `PDF page 1: Classic Spritz | EUR 7.50`. The review must independently compare every entry with the rendered page, including conditional terms, serving and whether a service fee is mandatory. Hold any uncertain item. Image PDF offers currently admit regular prices only; fee, fee-coverage and conditional price rows require another reviewed source format.

Set `source_sha256` to SHA-256 of the exact owner PDF bytes. Set `source_text_sha256` to SHA-256 of canonical UTF-8 JSON of `{"pdf_sha256":"<source_sha256>","evidence":<image_evidence sorted by offer_id>}`, with sorted object keys, no insignificant whitespace and unescaped Unicode (`ensure_ascii=False`). `image_review_digest(source_sha256, image_evidence)` computes this value. The existing D1 column name stores a digest bound to **both** the raw PDF and reviewed evidence; this is not a hash of PDF text. A changed PDF with a reused source ID conflicts with the immutable D1 row even if the price transcription stays the same. The protected importer re-fetches the PDF, rejects changed bytes, extractable text, unexpected page count, incomplete evidence or an offer that does not match its reviewed transcription. `pdfinfo` and `pdftotext` from Poppler must be available. This machine check cannot prove that a reviewer transcribed a page correctly; independent visual review of the exact raw PDF is required before approving a seed. Keep image-only candidate manifests in draft PRs until that review is complete. Never commit the owner PDF or OCR output merely to construct a manifest. The synthetic image-only PDF under `fixtures/` tests this code path but is not seed data.

Every offer has a stable ID, actual menu item name, original currency and exponent, positive minor-unit amount, optional category, exact serving label and/or millilitres, regular/happy-hour/conditional context and evidence pointer. Do not infer serving, expand a price range, or convert GBP to EUR. Every mandatory fee has a separate fixed minor-unit amount or a percentage in basis points, basis (person/table/bill/unspecified), and explicit applicability (all orders, conditional, or unknown). A fee is never silently folded into the displayed drink price. Absent fee coverage means **unknown**, not free. `documented_partial` means the known fees are not necessarily exhaustive. `explicit_no_fee` requires an independently reviewed owner statement and cannot coexist with fee rows.

An owner-stated **minimum spend** is separate from both offers and additive fees. A `minimum_spends` row has `id`, `venue_key`, `cell`, `source_id`, `label`, positive `amount_minor`, original `currency` and `currency_exponent`, `basis: "person"`, `applicability: "all_orders" | "conditional"`, paired `condition_text` (required for conditional, null for all orders), and concise `evidence_ref`. Its approved HTML/PDF text source must be pinned and independently reviewed. The importer never adds the minimum to a drink amount, converts it into a service fee, or changes customer submissions. Migration `0017_mobile_menu_v2_minimum_spends.sql` creates a distinct source-bound table and approved-source guard.

The existing app-only venue and cell GETs return `minimum_spends` as a separate array, with original amount, basis, applicability, condition and source. A client may request affected venues only after it renders this information by sending the exact query `minimum_spend=1` on both GETs. Without that marker, venue detail returns 404 for an affected venue and cell discovery omits it; invalid marker values return 400. This protects older installed apps from displaying an apparently cheap drink without its conditional order requirement. Distribute and test capable iOS, Android and Windows clients before seeding any minimum-spend venue. The website and legacy EUR price contract remain unchanged.

## Review and execution

1. Independently check the owner's menu, venue identity, source terms, each name/serving/price, mandatory fees and scope. Hold ambiguous branches, pricing, rights or fee statements. The minimum Google review count has been removed by the owner.
2. Add the exact manifest file to a reviewed PR. Run the preservation test. Do not tag a PR commit: the protected workflow requires the commit to be on `main`.
3. Create a lightweight `mobile-menu-v2-audit/<manifest-sha256>` tag at a reviewed main commit. Its protected dry run re-fetches public identity/source text, attests the existing production D1 binding, checks hidden/reported venues and conflicts, writes no rows, and uploads a receipt.
4. Only after the v2 app clients display named items, original currency, servings and separate fee scope, independent source review is complete, and the audit receipt is inspected, create a distinct lightweight `mobile-menu-v2-seed/<manifest-sha256>-<successful-audit-run-id>` tag on the **same main commit**. The workflow verifies the successful protected audit run and manifest/source pins before guarded writes.
5. Inspect the seed receipt and read back public v2 routes on supported phone builds. A complete receipt means D1 writes finished, not that App Store/Play production clients are live.

The importer is idempotent for identical rows and rejects conflicting IDs. D1 writes are individually guarded against hidden, moderated or reported venues. If a run fails after some writes, the receipt says incomplete; fix the cause and rerun the same pinned manifest only after inspecting inserted rows. No automatic rollback or overwrite occurs. Credentials are read only from the existing protected GitHub Actions secrets and never appear in manifests or receipts. Source research alone is never a live seed.
